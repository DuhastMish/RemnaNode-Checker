# Развёртывание nodecheck

Пошаговая инструкция: от чистого VPS до работающих страниц `https://admin.example.com`,
`https://status.example.com` и чекеров в нужных сетях. Время: около часа, если домен и VPS уже есть.

## Быстрый запуск

Нужны: VPS с публичным IP (Debian/Ubuntu), свободные порты 80 и 443, домен и API-токен панели-источника.
Если 443 уже занят (VPN-нода, другой сайт), задайте в `.env` `HTTPS_PORT=4443`: панель будет на
`https://admin.example.com:4443`. Порт 80 должен оставаться свободным — через него выдаётся сертификат.

**1. DNS.** У регистратора — две A-записи на IP VPS:

```
admin.example.com   A   <IP VPS>
status.example.com  A   <IP VPS>
```

**2. Панель на VPS** (от root). Сначала подставьте свои значения в первые три строки:

```bash
ADMIN_HOST=admin.example.com     # домен панели
STATUS_HOST=status.example.com   # домен status-страницы
TTYD_USER=user                   # пользователь VPS для веб-терминала

curl -fsSL https://get.docker.com | sh
apt-get install -y git openssh-server
git clone https://github.com/DuhastMish/RemnaNode-Checker.git /opt/nodecheck
cd /opt/nodecheck && cp .env.example .env
sed -i "s|^ADMIN_HOST=.*|ADMIN_HOST=$ADMIN_HOST|; s|^STATUS_HOST=.*|STATUS_HOST=$STATUS_HOST|; s|^TTYD_USER=.*|TTYD_USER=$TTYD_USER|" .env
docker compose up -d --build
docker compose logs app | grep -E 'ADMIN_TOKEN|PIN'
```

Поднимутся панель, веб-терминал и Caddy. Caddy сам получит HTTPS-сертификаты на оба домена (это займёт
до минуты). Последняя команда покажет сгенерированные admin-токен и PIN — сохраните их.

**3. Первая настройка.** Откройте `https://admin.example.com` и войдите admin-токеном.

- **Источники → Добавить источник:** тип, URL панели, API-токен.
- **Чекеры → Добавить:** панель покажет готовую команду.

**4. Чекер** — на каждой машине в той сети, из которой нужно проверять ноды (не на VPS панели):

```bash
curl -fsSL https://get.docker.com | sh
docker run -d --name nodecheck-agent --restart unless-stopped \
  ghcr.io/duhastmish/remnanode-checker-agent:latest admin.example.com nck_…   # команда из панели
```

Через минуту чекер станет `online` на странице «Чекеры», и плитки нод окрасятся. Подробности по каждому
шагу и другие варианты (свой nginx, панель дома за NAT) описаны ниже.

## Как это устроено

```
   Remnawave / Open60 (источники нод)
              │  синхронизация (pull)
              ▼
   ┌──────────────────────┐    HTTPS, токен чекера    ┌────────────┐ ┌────────────┐
   │ Панель               │◀──────────────────────────│ Чекер A    │ │ Чекер B    │ …
   │ UI, ноды, агрегация, │   heartbeat / nodes /     │ дом, ISP 1 │ │ моб. сеть  │
   │ алерты, экспорт      │   results (поллинг)       └────────────┘ └────────────┘
   └──────────────────────┘
          ▲ HTTPS (Caddy в составе панели / nginx)
       браузер
```

- **Панель** хранит источники, ноды, настройки и результаты, считает итоговый цвет нод, шлёт алерты и
  экспорт. **Сама панель ничего не проверяет.**
- **Чекер** — маленький контейнер. Ставится в ту сеть, **из которой** нужно проверять ноды: домашний
  интернет, мобильная сеть, дата-центр. Сам подключается к панели (только исходящие соединения, NAT не
  мешает), забирает список нод, проверяет их и отправляет результаты.
- **Два режима по домену.** Admin (вход по токену): всё, включая IP, настройки, чекеры, терминал.
  Status (вход по PIN): плитки нод и проверка одной ноды.

Как читать цвета, описано в разделе «Дополнительно».

## Что понадобится

| Что | Требования |
|---|---|
| VPS для панели | Linux с Docker и публичным IP (проверено на Debian 12), 1 ГБ RAM |
| Домен | две A-записи на IP VPS: `admin.example.com` и `status.example.com` |
| Машины для чекеров | любые Linux-машины с Docker в нужных сетях (не машина панели) |
| Источник нод | API-токен панели Remnawave и/или ADMIN_TOKEN Open60 |

Дальше в примерах используются `admin.example.com`, `status.example.com` и пользователь `user`.
Подставьте свои значения.

> Панель можно поставить и дома, за NAT, с обратным SSH-туннелем до VPS — см. «Панель за NAT» в конце.
> Основной вариант ниже — панель прямо на VPS.

## Шаг 1. DNS

У регистратора домена создайте две A-записи на IP VPS:

```
admin.example.com   A   <IP VPS>
status.example.com  A   <IP VPS>
```

Проверить: `ping admin.example.com` показывает IP VPS.

## Шаг 2. Панель на VPS

### 2.1. Docker, код, `.env`

```bash
sudo -i
curl -fsSL https://get.docker.com | sh
apt-get install -y git openssh-server
mkdir -p /opt && cd /opt
git clone https://github.com/DuhastMish/RemnaNode-Checker.git nodecheck
cd nodecheck
cp .env.example .env
nano .env
```

| Переменная | Что указать |
|---|---|
| `ADMIN_TOKEN` | длинная случайная строка (`openssl rand -base64 32`). Пусто — сгенерируется и выведется в лог |
| `PIN` | PIN для status-страницы. Пусто — сгенерируется 6-значный и выведется в лог |
| `ADMIN_HOST` | `admin.example.com` — домен панели: на него Caddy получает сертификат, его же панель подставляет в команду запуска чекера |
| `STATUS_HOST` | `status.example.com` — **обязательно**, по нему включается режим status |
| `HTTPS_PORT` | `443`; если занят — другой, например `4443` (адрес панели станет `https://admin.example.com:4443`) |
| `COMPOSE_PROFILES` | `caddy` — вместе с панелью поднимается встроенный Caddy (HTTPS) |
| `BIND_HOST` | `127.0.0.1`: панель доступна только через веб-сервер на этой машине |
| `TTYD_USER` | пользователь VPS для веб-терминала. Без него контейнеры не запустятся |
| `TTYD_IFACE` | `lo` |

`ADMIN_TOKEN` и `PIN` из `.env` используются только при первом запуске, дальше меняются в
«Настройки → Доступ».

### 2.2. Запуск

```bash
docker compose up -d --build
docker compose logs app | grep -E 'ADMIN_TOKEN|PIN'    # если не задавали их в .env
```

`docker compose ps` должен показать `nodecheck`, `nodecheck-ttyd` и `nodecheck-caddy` в состоянии `running`.

### 2.3. HTTPS

Отдельно ставить ничего не нужно: Caddy — сервис `caddy` в `docker-compose.yml`, поднимается вместе с
панелью (`COMPOSE_PROFILES=caddy`). Он сам получит сертификаты для `ADMIN_HOST` и `STATUS_HOST` и будет
проксировать оба домена на `127.0.0.1:8000`, а `/ttyd/` — на терминал (`127.0.0.1:7681`). Конфиг —
[deploy/Caddyfile](../deploy/Caddyfile), домены подставляются из `.env`. Порты 80 и 443 должны быть свободны.

Логи: `docker compose logs caddy`. Сертификаты хранятся в томе `caddy_data` и переживают пересоздание
контейнера.

Если на VPS уже работает nginx, оставьте `COMPOSE_PROFILES` пустым и возьмите за основу [deploy/nginx-nodecheck.conf.template](../deploy/nginx-nodecheck.conf.template):

- **nginx установлен на хосте:** `proxy_pass http://127.0.0.1:8000` и `http://127.0.0.1:7681`.
- **nginx в Docker-контейнере:** `127.0.0.1` внутри контейнера — это сам контейнер. Укажите в `.env`
  `BIND_HOST=0.0.0.0` и `TTYD_IFACE=docker0` (или bridge-интерфейс сети nginx), в `proxy_pass` — gateway
  Docker-сети nginx (`docker network inspect <сеть> --format '{{range .IPAM.Config}}{{.Gateway}}{{end}}'`)
  с портами `8000` и `7681`, и закройте порт 8000 снаружи файрволом:
  `ufw allow from 172.16.0.0/12 to any port 8000,7681 proto tcp && ufw deny 8000/tcp`.

Проверить: `https://admin.example.com` открывает страницу входа.

## Шаг 3. Первая настройка панели

Войдите на `https://admin.example.com` admin-токеном.

1. **Источники → Добавить источник.** Тип (Remnawave или Open60), имя вкладки, URL панели и API-токен.
   После «Добавить и синхронизировать» на главной появится вкладка с нодами. Пока они серые: проверять
   ещё некому.
2. **Настройки → Проверки (параметры для чекеров):** интервал плановой проверки, число воркеров,
   попытки SSH, таймаут и **URL пробы через прокси**, если используете проверку через прокси (см.
   «Как читать цвета»). Чекеры получают эти параметры сами.
3. **Настройки → Алерты** (необязательно): URL вебхука, куда слать уведомления.
4. **Источники → Экспорт** (необязательно): URL, куда раз в интервал проверки отправлять состояние нод
   этого источника.

## Шаг 4. Чекеры

### 4.1. Зарегистрировать чекер в панели

**Чекеры → Добавить**, имя (например, «Дом · провайдер 1»). Панель один раз покажет готовую команду
запуска: домен панели (из `ADMIN_HOST`) и токен `nck_…`. Скопируйте её сразу: в панели хранится
только хэш токена.

### 4.2. Запустить на машине чекера

На машине в нужной сети:

```bash
curl -fsSL https://get.docker.com | sh
docker run -d --name nodecheck-agent --restart unless-stopped \
  ghcr.io/duhastmish/remnanode-checker-agent:latest admin.example.com nck_xxxxxxxx
```

Образ собирается из репозитория [RemnaNode-Checker-Agent](https://github.com/DuhastMish/RemnaNode-Checker-Agent)
(там же `docker-compose.yml` и описание параметров).

Чекеру нужен только исходящий доступ к панели по HTTPS и к проверяемым нодам. Входящие порты и
белый IP не нужны.

Логи: `docker logs -f nodecheck-agent`. В течение минуты появится `подключён к панели`, затем сводка
`плановая проверка: N целей … отправлено N`. Адреса нод в лог не пишутся.

## Шаг 5. Проверка

1. **Чекеры:** у каждого статус `online`, есть версия и внешний IP.
2. **Ноды:** плитки окрашиваются после первой проверки, примерно через минуту после запуска чекера.
3. На карточке ноды нажмите **«Проверить сейчас»**: задание выполнят все online-чекеры, итог появится
   на странице задания.
4. `https://status.example.com`, вход по PIN: плитки и вкладка «Проверить».

Если всё так, развёртывание закончено.

## Дополнительно

### Как читать цвета

Каждый чекер присылает свой результат:

- зелёный — проба через прокси прошла, а если прокси-порта нет — SSH отвечает;
- жёлтый — SSH отвечает, прокси нет;
- красный — не отвечает ничего.

Чекер считает ноду **упавшей**, если два его результата подряд не зелёные. Цвет плитки — итог по всем
online-чекерам:

| Плитка | Значит |
|---|---|
| зелёный | ни один чекер не считает ноду упавшей |
| оранжевый | часть чекеров считает ноду упавшей (недоступна из некоторых сетей) |
| красный | все чекеры считают ноду упавшей |
| серый | нет свежих результатов ни от одного online-чекера |

SSH проверяется на 22-м порту. Проверка через прокси делается только для нод с портом прокси (его отдаёт
Open60) и только если задан «URL пробы через прокси». Этот URL должен вернуть
`{"ok": true, "ip": "<IP, с которого пришёл запрос>"}`.

### Одна нода в двух источниках

Если одна физическая нода заведена и в Remnawave, и в Open60, откройте её карточку и нажмите
«Связать» (панель подсказывает ноды с тем же адресом). Проверка станет одной, состояние — общим, а на
вкладках источников ноды останутся отдельными. Порт прокси подхватится от ноды Open60.

### Алерты

`POST` на URL из «Настройки → Алерты», заголовок `Authorization: Bearer <токен>`, если токен задан.
Отправляются в таких случаях:

- **нода** — открытие инцидента (плитка стала оранжевой или красной), смена оранжевый ↔ красный,
  закрытие (снова зелёная);
- **чекер** — пропал (нет heartbeat дольше порога) или снова на связи.

Серый цвет алертов не вызывает. Формат — в [README](../README.md#алерты).

### Экспорт в источники

Раз в интервал плановой проверки каждому источнику с заданным «Экспорт: URL приёма» уходит снимок
состояния всех его нод. Формат — в [README](../README.md#экспорт).

### Исходящий VPS

Если алерты и экспорт не должны уходить с IP панели, задайте прокси в «Настройки → Исходящий VPS»:
`ssh` (SOCKS через `ssh -D`), `socks5` или `http`. «Проверить» покажет внешний IP.

### Обновление

Панель:

```bash
cd /opt/nodecheck && git pull && docker compose up -d --build
```

Чекер (на каждой машине):

```bash
docker pull ghcr.io/duhastmish/remnanode-checker-agent:latest
docker rm -f nodecheck-agent
docker run -d --name nodecheck-agent --restart unless-stopped \
  ghcr.io/duhastmish/remnanode-checker-agent:latest admin.example.com nck_…
```

Токен запущенного чекера: `docker inspect nodecheck-agent --format '{{.Args}}'`.

Проверки совместимости версий нет: обновляйте панель и чекеры вместе.

### Резервная копия

Всё состояние панели находится в `./data/panel.db` (источники, ноды, настройки, история, чекеры).
Копируйте его при остановленном контейнере. Чекеры состояния на диске не хранят.

### Панель за NAT (дома) с туннелем до VPS

Если панель должна стоять дома, а наружу её нужно открыть через VPS:

1. На домашней машине в `.env` укажите `BIND_HOST=0.0.0.0`, оставьте `COMPOSE_PROFILES` пустым (Caddy нужен
   на VPS, а не дома) и запустите панель (шаг 2.1–2.2).
2. На VPS поднимите Caddy с [deploy/Caddyfile](../deploy/Caddyfile), заменив порты `8000 → 18000` и
   `7681 → 17681`. Для nginx в Docker используйте [deploy/nginx-nodecheck.conf.template](../deploy/nginx-nodecheck.conf.template):
   в нём `172.18.0.1` — gateway Docker-сети nginx, узнать его можно так:
   `docker network inspect <сеть> --format '{{range .IPAM.Config}}{{.Gateway}}{{end}}'`.
3. Откройте `http://<IP домашней машины>:8000` → **Настройки → Туннель панель ↔ VPS**: транспорт `ssh`,
   IP, логин и пароль VPS. В поле «SSH: адрес на VPS для пробросов» укажите `127.0.0.1` для Caddy на хосте
   или gateway Docker-сети для nginx в Docker. Нажмите «Сохранить», затем **«Настроить VPS автоматически»**.
4. Через 20–60 секунд статус должен быть «туннель активен», а «Проверить с VPS» — успешным.

Режим `wireguard` в тех же настройках работает только там, где провайдер не блокирует WireGuard. Для
него нужны `modprobe wireguard` на домашней машине и `TTYD_IFACE=wg0`, а прокси на VPS направляется на
`10.8.0.2:8000` и `10.8.0.2:7681`.

## Безопасность

- В `./data/panel.db` открытым текстом лежат токены источников, экспорта, вебхука и пароли VPS.
  Ограничьте доступ к машине панели. Токены чекеров хранятся только в виде хэша.
- Чекеры ставятся на **доверенные** машины: чекер знает адреса нод (без имён и источников), и их видно
  в его сетевом трафике. Если чекер скомпрометирован, нажмите «Отключить» или «Перевыпустить токен».
- Токен чекера даёт доступ только к `/api/v1/agent/*`, не к интерфейсу.
- `BIND_HOST=127.0.0.1` закрывает порт 8000 снаружи. Если панель слушает `0.0.0.0`, admin-режим
  доступен по `http://IP:8000` — закройте порт файрволом.
- Путь `/ttyd/` защищён только паролем пользователя `TTYD_USER`, admin-токен к нему не применяется.
  Задайте стойкий пароль или удалите сервис `ttyd` и блок `/ttyd/*` в конфигурации веб-сервера.

## Неполадки

| Симптом | Что проверить |
|---|---|
| `docker compose up` пишет `set TTYD_USER in .env` | в `.env` не задан `TTYD_USER` |
| Не помню токен или PIN | `docker compose logs app \| grep -E 'ADMIN_TOKEN\|PIN'`, или значение из `.env` |
| Источник: HTTP 401/403 | неверный токен источника |
| Все плитки серые | нет online-чекеров (страница «Чекеры») или первая проверка ещё не прошла |
| Чекер: `панель отклонила токен (401)` | токен скопирован не полностью или перевыпущен |
| Чекер: `(403)` | чекер отключён в панели |
| Caddy: `listening on :443: bind: address already in use` | 443 занят другим сервисом (`ss -ltnp \| grep :443`): задайте `HTTPS_PORT=4443` в `.env`, `docker compose up -d` |
| Caddy: `:80: bind: address already in use` | порт 80 нужен для выдачи сертификата: освободите его или используйте свой веб-сервер (`COMPOSE_PROFILES=`) |
| Чекер: `адрес панели должен быть https://` | в `.env` панели не задан `ADMIN_HOST`: задайте, перезапустите панель и перевыпустите токен |
| Чекер: `панель недоступна` | DNS/HTTPS до панели с машины чекера: `curl -I https://admin.example.com` |
| Чекер online, но плитки серые | интервал проверки ещё не прошёл; на карточке ноды нажмите «Проверить сейчас» |
| Домен открывает admin вместо status | `STATUS_HOST` в `.env` не совпадает с доменом; затем `docker compose up -d` |
| 502 на домене | панель не запущена или веб-сервер проксирует не на тот адрес/порт |

Логи панели: `docker compose logs app --tail 100`. Логи чекера: `docker logs nodecheck-agent --tail 100`.
