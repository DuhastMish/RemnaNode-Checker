# Развёртывание nodecheck

Пошаговая инструкция: от чистой Linux-машины и VPS до работающих страниц
`https://admin.example.com` и `https://status.example.com`.
Время: около часа, если домен и VPS уже есть.

## Как это устроено

```
браузер ──HTTPS──▶ VPS (Caddy или nginx) ──обратный SSH-туннель──▶ чекер ──▶ проверяемые ноды
```

- **Чекер** — любая Linux-машина с Docker: мини-ПК, домашний сервер, Raspberry Pi, виртуальная машина.
  Ноды проверяются **из той сети, где стоит чекер**, поэтому место выбирайте под задачу. Например, чтобы
  видеть ноды так, как их видит обычный абонент провайдера, чекер ставят в домашней сети.
  На нём работают два контейнера: `app` (веб-интерфейс, планировщик, проверки) и `ttyd` (веб-терминал).
- **VPS** нужен только для того, чтобы страницы были доступны из интернета: у чекера может не быть белого IP
  (домашнее подключение, NAT). Чекер сам открывает SSH-соединение к VPS и пробрасывает туда свои порты (`ssh -R`).
  На VPS ничего из проекта не устанавливается, только веб-сервер с HTTPS.
- **Два режима по домену.** Admin (вход по токену) показывает IP, историю, ручные проверки, терминал и
  настройки. Status (вход по PIN) показывает только цвета нод без IP и позволяет проверить одну ноду.

## Что понадобится

| Что | Требования |
|---|---|
| Чекер | Linux с Docker (проверено на Debian 12), 1 ГБ RAM, подключение к сети, из которой нужно проверять ноды |
| VPS | Linux с публичным IP, вход по SSH **по паролю** (root или пользователь с `sudo` без пароля) |
| Домен | две A-записи на IP VPS, например `admin.example.com` и `status.example.com` |
| Источник нод | API-токен панели Remnawave и/или ADMIN_TOKEN Open60 |

Дальше в примерах используются `admin.example.com`, `status.example.com` и пользователь `user` на хосте чекера.
Подставьте свои значения.

---

## Шаг 1. DNS

У регистратора домена создайте две A-записи на IP вашего VPS:

```
admin.example.com   A   <IP VPS>
status.example.com  A   <IP VPS>
```

Проверить: `ping admin.example.com` должен показывать IP VPS. Обновление DNS может занять до часа,
можно пока переходить к следующим шагам.

## Шаг 2. Чекер

### 2.1. Docker и SSH-сервер

```bash
sudo -i
curl -fsSL https://get.docker.com | sh
apt-get install -y openssh-server git
usermod -aG docker user          # user — ваш обычный пользователь на хосте чекера
```

`openssh-server` нужен для веб-терминала: ttyd открывает SSH-сессию на сам хост чекера под пользователем
`TTYD_USER` и спрашивает его пароль. Если терминал не нужен, этот пакет можно не ставить.

### 2.2. Код и `.env`

```bash
mkdir -p /opt && cd /opt
git clone https://github.com/DuhastMish/RemnaNode-Checker.git nodecheck
cd nodecheck
cp .env.example .env
nano .env
```

Заполните `.env`:

| Переменная | Что указать |
|---|---|
| `ADMIN_TOKEN` | длинная случайная строка, например из `openssl rand -base64 32`. Пусто — сгенерируется и выведется в лог |
| `PIN` | PIN для status-страницы. Пусто — сгенерируется 6-значный и выведется в лог |
| `ADMIN_HOST` | `admin.example.com` |
| `STATUS_HOST` | `status.example.com` — **обязательно**, по нему приложение включает режим status |
| `TTYD_USER` | пользователь хоста чекера для веб-терминала (`user`). Без него контейнеры не запустятся |
| `TTYD_IFACE` | `lo` для SSH-туннеля (по умолчанию), `wg0` только для режима WireGuard |
| `VANTAGE` | метка точки проверки в экспорте, например `home` |

`ADMIN_TOKEN` и `PIN` из `.env` используются только при первом запуске. Потом они хранятся в базе
и меняются в разделе «Настройки → Доступ».

### 2.3. Запуск

```bash
docker compose up -d --build
docker compose logs app | grep -E 'ADMIN_TOKEN|PIN'    # если не задавали их в .env
```

Проверить: `docker compose ps` показывает контейнеры `nodecheck` и `nodecheck-ttyd` в состоянии `running`.

## Шаг 3. Первая настройка из локальной сети

Откройте `http://<IP чекера в локальной сети>:8000`, войдите admin-токеном и перейдите в **Настройки**.

### 3.1. Источники нод

Заполните то, что используете (второй источник можно оставить пустым):

- **Remnawave URL**: адрес панели, например `https://panel.example.com`.
  **Remnawave токен**: API-токен из панели Remnawave.
- **Open60 URL**, **Open60 ADMIN_TOKEN**, **URL пробы через прокси**: если используете Open60.
  Это те же ноды, но с дополнительной проверкой через прокси (см. «Как читать цвета» ниже).

Нажмите **«Проверить подключение»**. Должно показать `Remnawave: N нод`. Затем нажмите **«Сохранить»**.
Список нод появится на главной в течение минуты.

С этого момента проверки уже работают в локальной сети. Следующие шаги нужны, чтобы страницы были доступны
из интернета.

## Шаг 4. Веб-сервер на VPS

Сначала выберите, куда чекер будет пробрасывать порты на VPS. Это значение настройки
**«SSH: адрес на VPS для пробросов»**:

| Ваш веб-сервер на VPS | Адрес для пробросов |
|---|---|
| Caddy или nginx установлены прямо на VPS (не в Docker) | `127.0.0.1` |
| nginx работает в Docker-контейнере | gateway Docker-сети этого nginx, обычно `172.17.0.1` или `172.18.0.1` |

Порты на VPS по умолчанию: `18000` (приложение) и `17681` (терминал).

### Вариант А. Caddy на VPS (проще всего: сертификаты получаются автоматически)

```bash
apt-get install -y caddy
```

`/etc/caddy/Caddyfile` (образец лежит в [deploy/Caddyfile](../deploy/Caddyfile)):

```caddy
admin.example.com {
    handle /ttyd/* {
        reverse_proxy 127.0.0.1:17681
    }
    reverse_proxy 127.0.0.1:18000
}

status.example.com {
    reverse_proxy 127.0.0.1:18000
}
```

```bash
systemctl reload caddy
```

### Вариант Б. nginx в Docker

Узнайте gateway Docker-сети, в которой работает nginx:

```bash
docker network inspect <сеть_nginx> --format '{{range .IPAM.Config}}{{.Gateway}}{{end}}'
```

Возьмите [deploy/nginx-nodecheck.conf.template](../deploy/nginx-nodecheck.conf.template), замените в нём
`172.18.0.1` на полученный адрес и `example.com` на свои домены, затем подключите файл к nginx.
Сертификат выпустите через `certbot certonly --standalone -d admin.example.com -d status.example.com`
(на время выпуска nginx нужно остановить, чтобы освободить порт 80).

Если на VPS включён `ufw`, разрешите контейнерам доступ к проброшенным портам на хосте:

```bash
ufw allow from 172.16.0.0/12 to any port 18000,17681 proto tcp
```

## Шаг 5. Туннель чекер → VPS

В **Настройках → Туннель чекер ↔ VPS** укажите:

| Поле | Значение |
|---|---|
| Транспорт | `ssh` |
| VPS: IP для SSH | IP вашего VPS |
| VPS: порт SSH | `22` или ваш |
| VPS: логин / пароль | root или пользователь с `sudo` без пароля |
| SSH: адрес на VPS для пробросов | из таблицы в шаге 4 |

Нажмите **«Сохранить»**, затем **«Настроить VPS автоматически»**. Приложение зайдёт на VPS, включит в
`sshd_config` опцию `GatewayPorts clientspecified` (нужна, чтобы привязать порт не к `127.0.0.1`) и
поднимет туннель. Через 20–60 секунд обновите страницу. Ожидаемый результат:

- статус «туннель активен»;
- кнопка **«Проверить с VPS»** отвечает `VPS видит приложение на …`.

Если адрес для пробросов `127.0.0.1` и вы не хотите давать приложению права root на VPS, можно
указать обычного пользователя без `sudo` и нажать **«Применить (перезапустить туннель)»** вместо
автонастройки: менять `sshd_config` в этом случае не нужно.

Туннель проверяется каждые 30 секунд и перезапускается, если упал. После перезагрузки чекера он
поднимается сам.

## Шаг 6. Проверка

1. Откройте `https://admin.example.com`, войдите admin-токеном. Видны плитки нод с IP.
2. Откройте **Терминал**: ttyd спросит пароль пользователя `TTYD_USER` на хосте чекера.
3. Откройте `https://status.example.com`, войдите по PIN. Видны плитки без IP и вкладка «Проверить».

Если всё открывается, развёртывание закончено.

## Дополнительно

### Как читать цвета

- **зелёный**: проверка через прокси прошла; если у ноды нет прокси-порта, SSH отвечает;
- **жёлтый**: SSH отвечает, прокси нет (провайдер режет порт или прокси на ноде не работает);
- **красный**: не отвечает ничего;
- **серый**: нет свежего результата (больше трёх интервалов проверки).

SSH проверяется на 22-м порту. Через прокси проверяются только ноды, для которых источник отдал порт
прокси (Open60), и только если задан «URL пробы через прокси». Этот URL должен вернуть
`{"ok": true, "ip": "<IP, с которого пришёл запрос>"}`.

### Исходящий VPS

Если запросы наружу (экспорт статусов) не должны идти с IP чекера, задайте второй VPS в
**Настройках → Исходящий VPS**: тип `ssh` (поднимется SOCKS через `ssh -D`), `socks5` или `http`.
Кнопка **«Проверить (показать внешний IP)»** должна показать IP этого VPS.

### Экспорт статусов

**Настройки → Экспорт статусов**: включите отправку и укажите URL и токен приёмника отдельно для нод
Remnawave и Open60. После каждой проверки туда уходит `POST` с JSON (формат описан в
[README](../README.md#экспорт-формат)) и заголовком `Authorization: Bearer <токен>`.

### Режим WireGuard

Есть вариант туннеля через WireGuard: он быстрее, но многие провайдеры его блокируют. Чтобы его включить:

1. `modprobe wireguard && echo wireguard >> /etc/modules` на хосте чекера;
2. `TTYD_IFACE=wg0` в `.env`, затем `docker compose up -d`;
3. транспорт `wireguard` в настройках, затем **«Настроить VPS автоматически»**: на VPS поставится
   WireGuard и добавится `[Peer]` чекера;
4. на VPS проксируйте на адрес чекера в туннеле (`10.8.0.2:8000` и `10.8.0.2:7681`) вместо
   `127.0.0.1:18000/17681`.

### Обновление

```bash
cd /opt/nodecheck
git pull
docker compose up -d --build
```

Настройки и история не теряются: они хранятся в `./data/nodecheck.db`.

### Резервная копия

Всё состояние находится в двух папках: `./data/` (база с настройками, токенами и историей) и
`./wireguard/` (ключи, только для режима WireGuard). Копируйте их целиком при остановленных контейнерах.

## Безопасность

- В `./data/nodecheck.db` открытым текстом лежат все токены и пароли VPS. Не публикуйте эту папку
  и ограничьте доступ к хосту чекера.
- Порт `8000` на чекере открыт в локальной сети, и через него доступен режим admin. Если локальная
  сеть не доверенная, закройте порт файрволом.
- Путь `/ttyd/` на admin-домене защищён только паролем пользователя `TTYD_USER`, вход по admin-токену
  к нему не применяется. Задайте этому пользователю стойкий пароль или удалите сервис `ttyd` из
  `docker-compose.yml` и блок `/ttyd/*` из конфигурации веб-сервера.
- Приложение заходит на VPS по паролю. Лучше завести для него отдельного пользователя
  (см. шаг 5), а не использовать root.

## Неполадки

| Симптом | Что проверить |
|---|---|
| `docker compose up` пишет `set TTYD_USER in .env` | в `.env` не задан `TTYD_USER` |
| Не помню токен или PIN | `docker compose logs app \| grep -E 'ADMIN_TOKEN\|PIN'`; если задавали в `.env`, то значение оттуда |
| «Проверить подключение»: HTTP 401/403 | неверный токен источника |
| Автонастройка: «неверный логин/пароль» | на VPS запрещён вход по паролю: `PasswordAuthentication yes` в `/etc/ssh/sshd_config` |
| «туннель упал сразу» | лог туннеля на странице настроек; частая причина: порт 18000 или 17681 на VPS уже занят |
| «VPS не достучался до …» | неверный адрес для пробросов (шаг 4) или `ufw` блокирует доступ из Docker |
| Домен открывает admin вместо status | `STATUS_HOST` в `.env` не совпадает с доменом; после правки выполните `docker compose up -d` |
| 502 на домене | туннель не поднят или веб-сервер проксирует на неверный адрес или порт |
| Все ноды серые | планировщик ещё не отработал; «Настройки → Запустить сейчас» у задачи «Плановая проверка» |

Логи: `docker compose logs app --tail 100`.
